# ADR-0022: Remote tabs — one control plane, tmux over ssh

## Status
Accepted (2026-10-10). Slice (a), terminal tabs, merged in PR #34. Slice (b), claude-code tabs, is §14–§20 below. Slice (c), a host badge in the UI, is not built. Review r1 (BLOCK: a dropped attach closed the tab and reaped live work; a failed create killed a live session of the same name; a workspace delete swallowed an unreachable host) amended §1, §5 and §8–§12.

## Context
On 2026-10-10 the host that runs purplemux (mdserver1) had 91 GiB of RAM, 69–78 GiB used, 2 GiB free and swap full (7/7 GiB), with about 6 orchestrators and 20 worker tabs. A second host, ai-server, had 373 GiB, 203 GiB available, and 64 cores. The owner asked for worker tabs that run on ai-server and appear in the mdserver1 workspace like local tabs: create, send, status, result and close, in the web UI and the phone app, and visible to the watchdog, Mission Control and notes.

Every tab today is one tmux session `pt-<ws>-<pane>-<tab>` on the local socket `purple`. Every tmux call goes through `src/lib/tmux.ts` with the session name, and `terminal-server.ts` attaches the browser with `tmux attach` under node-pty. Agent state comes from hooks that POST to `localhost:<port>` with the global CLI token (ADR-0020), and from local process and transcript reads.

## Options
1. **Federate two purplemux servers.** ai-server already runs its own purplemux (socket `purple`, port 8022, its own token). mdserver1 would proxy every tab route to it. Rejected: layouts, leases, the inbox, notes, the watchdog and Mission Control all assume that one server owns a tab. Each route would need a proxy, tab identities and tokens would cross servers, and ADR-0017 already rejected two servers over one set of tabs.
2. **Nested tmux.** A local session whose pane runs `ssh -tt ai-server tmux attach`. All local tmux calls work unchanged. Rejected: the local pane process is `ssh`, so process detection, cwd, scrollback and capture describe the ssh client, not the remote pane. A dropped connection leaves a local shell, and the next `tab send` runs its brief on mdserver1.
3. **One control plane; a tab has a host; tmux runs over ssh.** Chosen.

## Decision
1. **Registry.** Fleet config key `remote.hosts` (ADR-0019; the admin token or an orchestrator sets it) holds a comma-separated list of ssh aliases. Unset means no remote hosts. A name matches `^[A-Za-z0-9][A-Za-z0-9._-]{0,62}$`, so it is never an ssh option. The registry gates create only: a tab keeps its host for life, and its sends, status reads, attaches and closes still reach that host after the host leaves `remote.hosts`. Unregistering changes one thing: a close that then cannot reach the host drops the tab without a reap (§9).
2. **Tab attribute.** `ITab.host` is persisted in the layout. Absent means local. `tab create --host H` (CLI) and `host` (POST `/api/cli/tabs`) set it once; a tab never changes host. The tab list and `tab status` serve `host` (additive, ADR-0004). A host not in the registry is refused with `remote-host-invalid` (400, exit 2).
3. **Routing.** The session name stays `pt-<ws>-<pane>-<tab>`. `src/lib/session-host.ts` maps a session name to its host. It reads the session's workspace layout once and caches the answer on `globalThis`. A new remote session is registered before its tmux session exists. Every function in `tmux.ts` asks this map, and a remote call runs `ssh <host> tmux -L <socket> …` with the same tmux arguments. Local calls are unchanged.
4. **Remote socket and config.** The remote socket is `pmux-<origin hostname>`, never `purple`: the remote purplemux owns `purple`, and its scans must not see these sessions. Each create writes the local `tmux.conf` to `$HOME/.purplemux-remote/<origin>/tmux.conf` on the remote and starts the session with `-f` on that file.
5. **ssh.** `BatchMode=yes`, `ConnectTimeout=5`, `ServerAliveInterval=15`, `ControlMaster=no`, and `--` before the host. Timeouts: 5 s for a tmux call or a host check, 10 s for a create, 20 s for a close (the reap's 3 s grace and settle), none for an attach (a long-lived session; `ServerAlive` ends it about 45 s after the peer goes). No multiplexing: it saved about 15 ms per call, and its first connection from a fresh control directory exited 255 with no stderr in 1 of 10 tries (measured below). A master that loses its peer would also stall every call to that host until `ServerAlive` gives up (45 s), where one connection per call fails only the calls made during the outage.
6. **No pid crosses a host.** A remote pane pid is never returned to local code: `getSessionPanePid` answers null, `getAllPanesInfo` reports `pid: 0` with `host`, `getPaneDetailInfo` reports `pid: null`, and `observeSessionStrict` answers `unknown` for a present remote session. So no `/proc` read, `process.kill`, port scan or provider process check runs on a pid of another host. A remote agent's process is proven on its host instead (§19), and a remote tab is never designated orchestrator (§20).
7. **No remote path is read as local.** `getSessionCwd` keeps its contract, a local directory, and answers null for a remote session. The git, diff, file-content and session-list routes already treat null as "no directory". `git/sync` would otherwise run `fetch`, `pull` and `push` in the mdserver1 checkout that has the same path. `crossCheckLayout` never recreates a remote session locally, and remote tabs do not add their cwd to the workspace directories.
8. **Create.** The pane shell starts as `env -i … "$SHELL" -l` with the remote's own `HOME`, `USER`, `SHELL`, `LANG` and `XDG_RUNTIME_DIR`, plus `PMUX_TAB_ID` and `PMUX_WORKSPACE_ID` (the ADR-0016 reap marker). It gets no workspace token, no `CLAUDE_CONFIG_DIR` and no `GROK_HOME`: those name mdserver1 paths and secrets (slice (b) adds the tab's own token and `PMUX_URL`, §15). The cwd is the workspace directory; tmux starts a missing directory in the remote `HOME` (measured). The pane command is POSIX `sh` syntax run by tmux's default shell, so the remote account's login shell must be POSIX-compatible (bash, dash, zsh; not fish). The create is one `sh -s` script on stdin: refuse (exit 17) when the session name already exists, write the kit (§15), then `new-session … \; set-option … @pmux-create <nonce>`: the session is tagged with this call's random nonce in the same tmux command, so no dropped connection can leave it untagged (review r2). A name that already exists is never touched (review r1, B2: a cleanup that ran on `duplicate session` killed the live session of that name). A create that fails later removes a session only when it carries this call's nonce; a failure can come after `new-session` ran. An ssh failure (exit 255, a timeout) refuses with `remote-host-unreachable` (503, exit 6); the error names the exit status and stderr, never the script.
9. **Close and reap.** A remote close runs one shell script on the remote (`sh -s`). It finds the pane's descendants and every process of the user whose environment holds exactly `PMUX_TAB_ID=<tab>`, then sends SIGTERM to the pane's process group and to those processes, kills the session, waits up to 3 s, sends SIGKILL to survivors, and reports each process as `killed` or `survivor`. The result is `reaper: 'remote'`. Its audit entry is ADR-0016's `tab-reap` with `host` and without `sessionAlive` (the script does not report it). `--keep-processes` signals the pane group only. A close that cannot reach the host throws `remote-host-unreachable` and keeps the tab, because dropping it would leave the session running where nobody sees it. The one way out for a host that is gone for good: take it out of `remote.hosts`; a close of its tab that then fails over ssh goes ahead without a reap and writes a `tab-reap-skipped` audit entry. A close of several tabs (a pane, a workspace) asks every remote host first and closes the remote tabs before the local ones, outside the layout and store locks: a host that does not answer the check refuses the whole close (503) before any tab is reaped or any file changes (review r1, B3). That holds when the check itself fails. A host that answers the check and then fails a kill stops the close with 503 after the remote tabs before it were reaped; the layout and every local tab are unchanged, and a retry is safe: the reap of a session that is already gone kills nothing and reports it gone. A workspace delete stopped that way announces `aborted` only for the remote tabs it did not reap; a reaped one stays retired, so the watchdog does not report it dead.
10. **Attach.** The browser and phone attach through node-pty to `ssh -tt <host> tmux -u -L <socket> attach-session -t <name>`. The end of that ssh proves nothing about the session: a dropped connection, an sshd limit or a killed client end it too. The client reads close code 1000 as the session's end and closes the tab, and a tab close reaps the remote work (review r1, B1). So a remote attach closes with 1000 only when tmux on the host says the session is gone; otherwise, and when a connect finds the host silent, it closes with the new code 4001 (`REMOTE_ATTACH_LOST_CODE`), which the client retries with backoff like any unknown code. A connect to a session tmux says is gone closes with 1011 as for a local tab. 4001 is additive (ADR-0004).
11. **Unknown is not absent.** For a remote session, only tmux's own answer (`can't find session`, `no server running on`, `error connecting to … (No such file or directory)`) is absence; ssh failing or timing out is `unknown` (`sessionPresence`). `tab send`, `tab status`, `tab result`, the web and phone send route and a restart answer `unknown` with 503 `remote-host-unreachable` (exit 6, retryable), never `session-not-running` or `alive: false`; a restart never recreates a session over it.
12. **Status.** The poll merges `list-panes -a` from each host that owns a tab (the layouts are read once per process; a create registers its session, and a tab close, a pane close and a workspace delete forget theirs) into the pane map; a registered host with no tab is never asked. A host whose scan fails is skipped for 30 s, so a silent host costs one timeout per 30 s, not one per poll. A remote terminal tab reports `idle` when its foreground process is a shell and `running` otherwise; listening ports are not read.
13. **What a remote tab cannot do.** A web UI switch of a remote tab to an agent type, the web UI's agent launch, the Claude launch-command route, a timeline resume and the boot auto-resume all type or prepare this host's launch command; they refuse a remote tab (409 `remote-type-unsupported`, or a resume error) or skip it. A remote agent is launched by `tab create --host` only. `codex-cli` and `grok-cli` are refused at create (400 `remote-type-unsupported`, exit 2): Codex's managed launch proves its process on this host (ADR-0021), and Grok has no remote hook. A person can still run an agent by hand in a remote terminal tab; purplemux then shows a terminal.

Known limit (review r2, nit 4): `addTabToPane` holds the layout lock across the remote create (at most 10 s) and a restart holds it across the presence check and the create (at most 15 s). A silent host can hold every workspace's layout writes that long. Not redesigned here.

## Slice (b): claude-code tabs on a remote host
14. **Create.** `tab create -t claude-code --host H [--cwd DIR] [-m M] [-r E]`. The launch typed into the remote pane is `PATH="$HOME/.purplemux-remote/<origin>/bin":"$PATH" claude --settings <kit>/hooks.json --append-system-prompt-file <kit>/workspaces/<ws>/claude-prompt.md [--model] [--effort] [--dangerously-skip-permissions]` (the last when this server's config says so). The remote Claude uses the host's own login and `~/.claude`: credentials, MCP config and the session store stay per host.
15. **The kit.** Each remote create writes, under `$HOME/.purplemux-remote/<origin>/` on the host, in the same `sh -s` run: tmux.conf, `status-hook.sh` and `hooks.json`, this server's `bin/cli.js` with a `bin/purplemux` wrapper, the workspace prompt, and `tabs/<tab>.env`. The env file (0600) holds the tab's own token (`PMUX_TAB_TOKEN`, ADR-0010); the pane's launch sources it once and deletes it, so the token is never on a remote command line or in `pane_start_command`. The pane also gets `PMUX_URL`, this server's callback URL: fleet config `remote.callback-url`, else `http://<this hostname>:<port>`. A worker's `purplemux` (the kit's, first on Claude's PATH) reaches this server with its own token, so its commands act on this workspace.
16. **Hooks.** The remote hook posts Claude's raw hook JSON to `PMUX_URL/api/status/hook?remote=claude&event=<word>&session=<tmux session>` with the tab's token. The route accepts that token only for that tab's own session, and only while the session is remote; a tab token can never reach the local hook paths, whose body names the session. The session id and transcript path come from the body.
17. **Transcript.** Every reader of a transcript here reads a local file, so a remote transcript is copied to `~/.purplemux/remote-transcripts/<tab>/<session id>.jsonl` by bounded ssh reads of the bytes past the copy's length (4 MiB a read, 8 reads a sync), before each hook is applied, before each stop is read (and its 500 ms re-read), and on each poll while the tab is busy. Only a path `<abs>/projects/<project>/<session id>.jsonl` is read. A `mirror.json` beside the copy lets a restarted server resume it; every close path drops the copy. Subagent transcripts are not copied, so the background ledger (ADR-0018) sees only the main transcript's open work.
18. **Replay.** An event no server answers spools beside the remote hook in the ADR-0020 format. Each drain first moves those files into this server's spool, taking only a remote delivery for a remote session of that host, then the one drain replays them in time order against the tab's floor.
19. **Process proof.** `observeOrchestrationProcess` observes a remote tab's Claude on its host with one script: the session's pane id and pid, then the pane's descendants for the provider's executable, with pid and start time. So launch and turn evidence (ADR-0021) retires for a remote worker as for a local one. A remote close with no survivor and tmux-proven absence is a confirmed reap of pending work. The poll's "agent running" check for a remote pane is the pane's foreground command (`claude`).
20. **Never a coordinator.** A remote tab is refused as orchestrator before any runtime proof is asked (`orchestrator-candidate-invalid`): the coordinator's nudges, recovery and process proof are this host's.

## Feasibility, measured 2026-10-10 from mdserver1
- `ssh -o BatchMode=yes ai-server` works without a prompt. ai-server: Linux 7.0.0-34, uid 1000 `mdone`, `HOME=/home/mdone`, tmux 3.6 (mdserver1 also 3.6), Claude Code 2.1.295 (mdserver1 2.1.296).
- ssh round trip (shell `time`): about 70 ms without multiplexing, 50–60 ms multiplexed. A control path in the session scratch directory was refused: `ControlPath too long (… >= 108 bytes)`.
- From Node (`runSsh`, spawn included): 40 calls without multiplexing, 0 failures, median 86 ms, p90 102 ms, max 111 ms. With `ControlMaster=auto` + `ControlPersist`, the first call from each of 10 fresh control directories: 1 exited 255 with empty stderr (the first end-to-end create hit the same failure after the session was made; §8 now removes such a session).
- On a throwaway socket: `new-session -c /nonexistent/dir` exits 0 and the pane starts in `/home/mdone`; `send-keys` and `capture-pane` round-trip; `has-session -t =nope` exits 1 with `can't find session: nope`; after `kill-server`, `ls` exits 1 with `no server running on …`. ssh's own failure is exit 255, so the two are distinguishable.
- `kill-server` left a `( sleep 300 & )` and a `setsid sleep 301` of the pane alive; `grep -lzx PMUX_TAB_ID=<tab> /proc/[0-9]*/environ` found both among 1 863 processes in 56 ms.
- `claude` started in a throwaway remote session in `/tmp` and drew its composer within 10 s ("Claude Code v2.1.295 … Opus 5.5 (1M context)"); the session and every marked process were then removed.
- ai-server reaches `http://mdserver1:8022/api/health` and `http://100.94.44.114:8022/api/health` (200). mdserver1 listens on `0.0.0.0:8022` with `networkAccess: tailscale`, so a hook from ai-server passes the address filter.
- ai-server has its own `/home/mdone/code/nomupay` (separate clones; `treasury-api` on `main`, `engineering` on another branch), its own `gh` login (`mattdone-ai` active), AWS profiles and Claude credentials. No path is shared or mounted. `sshfs` exists on mdserver1, not on ai-server.

## Hard problems
| Problem | Slice (a) | Plan |
|---|---|---|
| tmux calls for a remote tab | solved: routed by session name | — |
| Terminal attach (web, phone) | solved: `ssh -tt … attach` | — |
| `tab result`, `tab send`, `tab status` | solved: capture-pane, send-keys and list-panes over ssh | — |
| Close: processes that escape the pane | solved: remote marker scan (§9) | — |
| A remote pid read as a local pid | solved: never returned (§6) | (b) adds a remote process proof |
| A remote cwd read as a local path | solved: null (§7) | (c) may show it as text |
| Agent state hooks | (a) refused | (b) solved: §16 (tab token), §18 (remote spool pulled and replayed) |
| Transcripts (timeline, ADR-0018 end lines, background ledger) | (a) refused | (b) solved by a local copy (§17); subagent transcripts are not copied |
| `purplemux` CLI inside a remote tab | (a) refused | (b) solved for a claude-code tab: the kit's CLI first on Claude's PATH, `PMUX_URL`, the tab token (§15). In a remote terminal tab the login shell's PATH puts the host's own `purplemux` first; it reads `PMUX_URL` only once the host runs a release with this change |
| Claude, gh and AWS credentials on the remote | not copied: each host uses its own login. AWS SSO expiry on ai-server is the ai-server login's problem | — |
| Worktrees and repo paths | not shared: a remote worker clones or creates its own worktree on the remote | — |
| MCP config | not copied: the remote's own `~/.claude` and `.mcp.json` apply | (b) names it per workspace |
| Host down | the poll shows its tabs without a pane (scans back off 30 s); send, status, result and restart answer 503; an attach closes 4001 and the client retries; no local session is ever created in its place; a close refuses until the host answers or is unregistered (§9) | — |

## What would disprove it
- A tmux call for a remote tab that reaches the local `purple` socket, or a local session created for a remote tab (§3, §7).
- A local process signalled, or a local `/proc` entry read, because of a remote tab (§6).
- A close that leaves a marked process alive on the remote and still reports no survivor (§9).
- Per-call ssh latency high enough that `tab send` to a remote tab misses its Enter where a local send does not; the measured p90 of 102 ms is well below the 600 ms gap of the two-Enter submit.

## Consequences
- RAM moves off mdserver1 only for work that runs in remote tabs; the tmux client and the ssh attach stay local (one ssh process per open terminal view).
- The server must hold a working non-interactive ssh login to every registered host. A host whose key or alias breaks shows its tabs as not running until it is fixed.
- A registered host costs one `list-panes` over ssh per status poll.
- Version skew between the two hosts (Claude Code 2.1.296 here, 2.1.295 there) is visible only inside the remote tab.
