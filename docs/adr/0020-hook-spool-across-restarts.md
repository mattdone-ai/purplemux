# ADR-0020: Hooks spool what no server answers; the next server replays it

## Status
Accepted (2026-09-27), h-selfimprove item `hook-gap`. Amends ADR-0017 (a deploy step before the restart, a spool step after a rollback). Review r1 (BLOCK) amended the floor, the boot drain, the bounds and the rollback path. Review r2 (BLOCK) moved the floor out of the layout into `hook-spool/.floors.json`, held the inbox's first tick for the first boot drain, made a drain wait for the tab scan, and narrowed the rollback set-aside. Review r3 (nits) made the boot drains wait for a rescan, set a non-draining server's leftover spool aside before a forward deploy, and named the 5xx and crash edges (§4).

## Context
Every agent state change reaches the server as a hook POST (`status-hook.sh`, `codex-hook.sh`, `grok-hook.sh`). The scripts ran `curl -s … 2>/dev/null` and exited 0 on any failure, and exited at once when `~/.purplemux/port` was absent. The server removes the port file on shutdown. So every event that fired between the stop and the new server's port file was lost: a turn that ended during a restart left its tab `busy` with no stop, and its orchestrator was never told. Measured 27 Sep ~15:00Z: the watchdog fix d1fd69bd was held back because a mid-turn tab in another workspace would have lost its events to the restart.

## Decision
1. **Spool on failure, in the hook.** Each script POSTs the body on stdin (`--data-binary @-`). When no server answers, it writes the event to `~/.purplemux/hook-spool/<epoch-ms>-<pid>-<rand>.json` (dir 0700): a dot-named temporary, then one rename. "No server answers" is: no port or token file; curl exit 3 (malformed URL, added by PMUX-REMOTE-URL r3), 5, 6 or 7; curl exit 28 with `time_connect` 0 (the connect never finished); or an HTTP answer that is not 2xx (5xx before PMUX-REMOTE-URL r3). Never spooled:
   - a 2xx answer, or a timeout after the connect: the server may have applied the event (amended by PMUX-REMOTE-URL r3,
     2026-11-14: every 3xx, 4xx and 5xx answer spools; the hook route answers them only before it applies anything, and
     a 308 from a callback URL that ended in `/` lost every event of a remote tab);
   - a connection the old server cut while it exited (curl 52/56): it may have applied the event too, and the release it replaces persists no floor (4), so a replay could repeat it (a second DONE nudge). Such an event is lost, as before this ADR; the tab it leaves `busy` becomes `unknown` at the restart and `resolveUnknown` rebuilds it from the transcript;
   - a session that is not purplemux's (`pt-*`): the Codex hook is global;
   - a `poll`, and Codex `PreToolUse` (one per tool call, no state).

   A body over 256 KiB (a Write's content, a long Bash output) is spooled as metadata only: `body: null`, `bodyDropped: true`, `bodyLength`. There is no retry: one round trip, then the file.
2. **The file contract** (one JSON object): `v` (`1`); `at`, when the hook fired, epoch ms, taken before the POST (`date +%s%N` cut to ms, never `%3N`, which uutils prints as raw nanoseconds; whole seconds where `%N` is absent); `session`; `query`, the route query string (`kind=tool&session=…`, `provider=codex&tmuxSession=…&generation=…`, empty for a Claude work-state event); `body`, the exact POST body embedded as JSON (`null` when empty or dropped); optional `bodyDropped` and `bodyLength`.
3. **Replay through the route's own code, after the server listens.** The route's handler is `dispatchHook({ query, body, replayedAt? })` (`src/lib/hook-dispatch.ts`); the route calls it without `replayedAt`, the drain with the file's `at` (never later than now). Drains:
   - `startBootHookSpoolDrains`, called once the server listens and has written its port file, never awaited: one drain at once and one 5 s later (a hook that saw no port file may rename its file after the first drain listed the spool). A large spool never holds up startup or the deploy's health gate; the drain yields to the event loop every 50 files;
   - at the start of every poll, started and never awaited: the liveness reconcile, the stuck checks and the idle nudges go on while a drain runs (amended 28 Sep, ppc-43: an awaited drain held every poll for 7 minutes). One drain runs at a time; a poll during a drain starts no second one. So a poll can decide on a tab before that tab's queued replays apply: its synthetic `session-start` is a live event that raises the floor to now and makes those replays history only (the newer observation wins), and the window is bounded by the per-event limit below.

   A drain is a no-op until `init()`'s scan has built the tabs, and while a rescan rebuilds them: an event for a tab not yet built would be counted as applied and deleted. The files wait for the next drain. The two boot drains wait for a scan in flight instead of skipping it, so the first one always drains. The inbox starts before the server listens, but its ticks are skipped until the first boot drain has finished (`bootHookSpoolDrained()`), at most 10 s; past that it starts anyway and logs it. Until that drain has run, a tab whose `prompt-submit` was spooled during the restart still looks `idle` or `ready-for-review`, and a notice could be pasted into an agent that is actually busy.

   Files apply oldest first by the time in their name and are deleted when applied. A file that does not parse, a stray name, a replay that throws (a 5xx event), or a replay that has not finished within 5 s (`HOOK_REPLAY_EVENT_TIMEOUT_MS`) moves to `hook-spool/bad/` once and is never retried; the drain goes on with the next file, so N replays that hang cost at most N × 5 s. A timed-out replay is abandoned, not cancelled: if it finishes later, its state change is ordered against the floor like any replay, and one log line names its file and says whether it applied or failed, and after how long. A drain that found files logs one line: applied, the replayed state events among them that were stale, timed out, bad, and the duration. Not dispatched, deleted with one log line: a file older than the replay window (1 h), the oldest beyond 10 000 files, and a metadata-only file. `bad/` entries are pruned after 7 days and orphaned temporaries after 10 minutes. A replayed Codex hook is checked for attribution only (`withReplayedCodexHookGeneration`): it applies when its generation is the tab's recorded active one, is skipped otherwise, and never holds the generation. It runs no process proof and takes no target lock (amended 28 Sep, ppc-43). Because it takes no lock, its layout read can predate a concurrent relaunch's `pending` write, so the launch the status manager tracks in memory decides too: a tracked `pending` launch or another generation skips the event (`launch-changed`). Both are live conditions: the proof checks the process running now, which says nothing about an event spooled during a restart, and the lock queued each replay behind the busy tab's live hooks, each running that proof (a `pgrep` per process-tree node, 4.8 s for one walk of a 30-descendant pane on the loaded host). Measured 28 Sep: 10 s to 130 s per replayed Codex event. A replayed legacy Codex hook (no generation) is skipped as unattributable, never sent through the lock and the model check. A skipped replay changes no state: it is recorded as a stale replay (history, the drain's stale count, one log line with the reason) and its file is deleted.
4. **Order against live events: a persisted floor, outside the layout.** Each tab's floor is the time of the latest hook STATE event applied to it (a live event's receipt time or a replayed event's `at`), or a restored watchdog stop's `at`. A metadata patch (Codex, Grok) is ordered against the floor but never raises it. The floors live in one small file, `hook-spool/.floors.json` (tab id → epoch ms, `HookFloorStore` in `src/lib/hook-floors.ts`). It is written by a temporary file and one rename, at most once per 5 s, and on graceful shutdown (awaited). The write sends no sync message. At boot the server loads the file before its tab scan and drops the floors of tabs that no longer exist; a closed tab's floor goes with the tab. The layout carries no floor: round 1 saved it there, and every Codex tool hook became a layout rewrite plus a `layout` sync message and a re-fetch in every browser. A layout that still carries `hookFloorAt` is read without error; the field is ignored.

   A replayed event older than the floor, or older than the replay window, changes no state. It is recorded in the tab's hook history (`getHookHistory`, the last 32 events, each marked `stale` or not), and a metadata patch returns `stale`. A later event is applied as a live one, dated at `at`: `lastEvent.at`, and a replayed stop's `turnEnd.at`. So the stop is classified normally, may nudge once, and the idle clock counts from the real stop.

   Why a floor that is too low is harmless, and so a 5 s save lag, a lost save and the missing metadata raise are safe across a restart: a spool file from the restart gap is written while no server answers, so its event is later than anything the stopped server applied. The floor only has to be at least the time of the events applied before the restart, and the gap spool holds none older. Within one server's life the floor is in memory at once.

   Not every spool file comes from a gap. A 5xx answer, or a connect that never finishes (curl 28 with `time_connect` 0), spools while a server is up. That server drains the file at its next poll against its in-memory floor, which is correct. The edge: the server crashes (no graceful shutdown, so no final save) before that poll. The saved floor can then be up to 5 s behind the events it applied live, and the next server can replay such a file although a live event of those last 5 s was newer, so that older event overwrites the newer state once. The next live hook of the tab, or `resolveUnknown` for a tab left `busy`, corrects it. It needs a 5xx or a stalled connect and a crash within one poll interval; it is accepted, not fixed. The one accepted edge: a replayed metadata patch that is older than a live metadata patch, with no live state event between them, restores the older summary or last user message until the next hook of that tab.
5. **Pre-install before a restart; set the spool aside after a rollback.** `deploy-live.sh` runs the release's own `scripts/install-hook-scripts.sh --dir ~/.purplemux` after the quiet wait and the backup and before the swap. The script renders the release's templates (`src/lib/hook-scripts.ts`) and replaces each script in one rename. The directory installer is in `src/lib/hook-scripts-install.ts`, which no Next route imports. Its `path.join(dir, name)` was a path Turbopack could not scope (other argument-built paths in the route graph trace cleanly, so this is one trigger, not a rule); in `hook-scripts.ts` it traced the whole project into `.next/standalone`, where `tsx` loaded a copy of `server.ts` in place of `server.js` and the release never started. `scripts/post-build.js` now refuses a standalone tree that holds a root-only file (`scripts/standalone-trace-check.cjs`). A forward deploy without the installer refuses (`HOOK-INSTALL-MISSING`, exit 2), a failed pre-install refuses before the swap (`HOOK-PREINSTALL-FAILED`, exit 1), and `--dry-run` renders into a scratch directory. After a HEALTHY rollback restart (automatic or `--rollback`) into a target that is not a release directory with the installer, the script moves `hook-spool/*.json` into `hook-spool/bad/rollback-<stamp>/` and reports the count in `HOOKS=`. Such a server never drains and saves no floor, so a later server could not order those files against the events it applied live. The check reads the release directory rolled back to, whose scripts and build come from one commit. A first install's live checkout is a working tree whose scripts need not match the build it runs, so it always counts as a server without this ADR, and `--rollback` to it runs no installer (`HOOKS=skipped (rollback target is not a release)`). When the rollback fails its own health gate, the spool stays and `HOOKS=` ends `rollback-unhealthy; spool kept`: the next server that comes up drains it against its own floor. A forward deploy whose running server does not drain (by the same test: not a release directory with the installer) first moves any `hook-spool/*.json` already there into `hook-spool/bad/stale-<stamp>/` and reports the count in `HOOKS=`, then installs the new scripts. Such files are leftovers of that server, for example a spool kept after an unhealthy rollback whose old release came up later: it applied events live and saved no floor, so a replay could overwrite newer state. `.floors.json` is never moved.

## Consequences
- A restart through `deploy-live.sh` into a release with this ADR loses no hook event from a purplemux tab that fired while no server answered. Two cases are still lost: an event whose POST the exiting server cut (curl 52/56), and an event spooled around a rollback into an older release (set aside, not replayed). In both cases the tab is rebuilt from the process and the transcript, as before.
- A replay never overwrites state newer than the tab's floor, across restarts too, and never repeats an end-line nudge: an older stop is history only, and a repeated end line is not re-sent.
- The pre-installed scripts post the same headers, URL and body as the old ones, but the Claude post-tool body now goes on stdin rather than as a `-d` argument. Bodies over the 128 KiB argument limit used to fail before curl ran; now they reach the server. That is harmless: the tool parser reads only the paths and the command.
- Anyone who can write `~/.purplemux/hook-spool/` can inject hook events without the CLI token. That user can already read `~/.purplemux/cli-token`, so the spool adds no new authority.
- The spool is bounded only by a draining server. While none runs (a long rollback), the writer-side limits (no PreToolUse, metadata-only large bodies) keep it small, and the next drain prunes it.
- Script writes are atomic everywhere (`writeScriptAtomic`): `sh` reads a script while it runs it, so an in-place rewrite could run half of each version.
